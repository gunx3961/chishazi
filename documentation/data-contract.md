# Spreadsheet Data Contract

Last updated: 2026-06-12

## Source of Truth

The application-level spreadsheet contract is defined in:

```text
src/Chishazi/DataDefinitions/SpreadsheetDefinition.cs
```

Update that file whenever a worksheet name, column name, column type, required
field, or validation constraint changes. Tests and parsers should reference
these definitions instead of duplicating worksheet contracts in configuration.

## Definition Boundary

A `WorksheetDefinition` is the largest unit of one data contract. Each
worksheet owns:

- its exact tab name
- its ordered set of known columns
- column data types
- required-field rules
- column validation flags
- references to controlled-value worksheets and multi-value separators

The spreadsheet definition is a collection of independent worksheet
definitions. Adding another worksheet does not change the browser cache format.

## Current Worksheets

### Recipe

Definition property: `SpreadsheetDefinition.Recipe`

| Column | Type | Required | Constraint |
| --- | --- | --- | --- |
| `name` | Text | Yes | Unique by convention |
| `description` | Text | No | None |
| `tags` | Text | No | Comma-separated references to `Tag.id` |

The first worksheet row contains column headers. Unknown columns are retained
in the raw cached snapshot even when the current business parser does not use
them. Tags are trimmed, empty entries are discarded, and duplicate tags are
removed case-insensitively while preserving their first spelling and order.
Unknown tag references remain visible but produce validation issues.

### Tag

Definition property: `SpreadsheetDefinition.Tag`

| Column | Type | Required | Constraint |
| --- | --- | --- | --- |
| `id` | Text | Yes | Unique, automatically generated opaque identifier |
| `displayName` | Text | Yes | User-managed display text |

`id` is generated by the application and stored by Recipe rows. It is not shown
or edited in the Tag management interface. `displayName` is the only Tag field
the user manages and may be changed without breaking Recipe references.

Tag rows are managed through `/data/tags`; the application does not contain a
static Tag list.

The previous `value`, `name`, and `active` contract is obsolete. An empty
local-only Tag worksheet is refreshed automatically. Existing remote rows must
be migrated to `id` and `displayName`; preserve each old `value` as the new
`id` until Recipe references are updated.

## Local Batch Mutation

`SpreadsheetMutationService` appends multiple rows by matching worksheet header
names. It preserves existing rows, unknown columns, and worksheet order. The
service operates on `WorksheetDefinition` and column-value dictionaries, so
future type routes can add arbitrary batches to the same working snapshot.

If a worksheet is missing when rows of that type are added, the service adds a
local-only worksheet using the definition name and ordered column names as its
header row. The worksheet receives a temporary negative ID. Local review and
upload preview expose this as a worksheet creation, and confirmed upload
creates the remote worksheet before writing its cells.

Only the worksheet required by the current mutation is initialized. Ordinary
cache reads do not create missing worksheets. Unknown remote worksheets remain
untouched.

## Cache Independence

The cache stores a schema-neutral `SpreadsheetSnapshot`:

- spreadsheet ID and title
- synchronization timestamp
- every worksheet's ID, index, name, and type
- all returned cell values for every worksheet

The cache does not validate, rename, select, or discard cells based on
`SpreadsheetDefinition`. Business parsers apply definitions after loading the
snapshot. This allows a new application version to reinterpret an existing
cache after the contract changes.

Google Sheets omits trailing empty rows and columns from value responses. The
snapshot therefore represents all returned values, not the spreadsheet's
allocated empty grid size or formatting.
